## Reusable gotchas discovered by prior layers (read before you start — avoids repeating known failures)
1. **Solution attachment**: the Python Dataverse SDK's `client.tables.create(..., solution=...)` does not reliably auto-attach the new table to the `poutineleaguecore` solution's component list — it can silently land only in the org Default Solution instead. After creating the table, EXPLICITLY verify it's a member of `poutineleaguecore` (e.g. query solutioncomponents or use pac solution list-components-equivalent check) and if missing, run `pac solution add-solution-component --component <table-logical-name> --componentType 1` (componentType 1 = Entity) to attach it, then re-verify.
2. **DateTime columns**: if Season needs a Start Date / End Date (check ARCHITECTURE.md for exact field names/types), creating a DateTime column via the SDK's generic `add_columns()`/`create()` with a plain `"datetime"` type string leaves `DateTimeBehavior` unset, which later breaks metadata operations on the entity with errors like `"Failure in generation Filtered<table>..."`. Neither entity-scoped nor org-wide Publish fixes this after the fact. Workaround: create DateTime columns via a raw Web API call with explicit `Format` (e.g. `DateOnly` or `DateAndTime` per the field's actual semantics) and `DateTimeBehavior` (e.g. `DateOnly` behavior for pure dates, `UserLocal` for date+time) set correctly from the start.
3. **Choice/status columns**: if Season has a status choice column (e.g. Active/Closed per ARCHITECTURE.md), use the standard dv-metadata choice-column creation flow (global or local choice set as appropriate) — no known gotcha here, just documenting since Season is expected to have one.
