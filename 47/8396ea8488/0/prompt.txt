## IMPORTANT: pre-made design decision (read carefully, do not re-litigate)
Dataverse cannot store an array/list inside a single row. The coordinating session already decided (autonomously, since the human was unavailable to confirm) how to model the "ranked entries" list. You must implement it exactly as follows and flag it prominently in your PR description for human review/adjustment:

1. **`rpo_SeasonResult`** (the header/snapshot record) — one row per season+category combination:
   - Lookup to `rpo_Season`
   - Lookup to `rpo_Category`
   - `computedat` — DateTime timestamp of when the nightly computation ran. **Apply the DateTime gotcha workaround (see below)** — create via raw Web API call with explicit Format (`DateAndTime`) and DateTimeBehavior (`UserLocal`), not the SDK's generic add_columns with a plain "datetime" string.
2. **`rpo_SeasonResultEntry`** (NEW 10th supporting table, one row per ranked entry within a Season Result) — relational decomposition of the "ranked entries" list, not new business scope:
   - Lookup to `rpo_SeasonResult` (parent — required, N:1)
   - `rank` — Whole Number (1 = top rank)
   - `score` — Decimal
   - Lookup to `systemuser` (employee) — NULLABLE, populated only when the parent Category's computation type is employee-based (e.g. Best Supporter, Best Critic). Use the direct-relationship workaround for systemuser lookups (see gotcha #2 below) with an explicit `rpo_`-prefixed relationship name (e.g. `rpo_SeasonResultEntry_Employee`).
   - Lookup to `rpo_PoutineSubmission` (poutine) — NULLABLE, populated only when the Category's computation type is poutine-based (e.g. Best Seller, Top Poutine). Exactly one of the two lookups should be populated per row, never both, never neither.

Do NOT model this as JSON/text blob or fixed top-N columns — the child-table approach was the decision made. If, after reading ARCHITECTURE.md yourself, you believe this decision is clearly wrong or conflicts with something explicit in the doc, stop and flag it back to the coordinator rather than proceeding silently — but do not just substitute your own alternative approach without flagging it.

## Reusable gotchas from prior layers
1. **Solution attachment**: SDK's `client.tables.create(..., solution=...)` doesn't reliably auto-attach new tables to `poutineleaguecore`'s solutioncomponent list. After creating EACH table (both rpo_SeasonResult and rpo_SeasonResultEntry), explicitly verify solution membership and fix with `pac solution add-solution-component --component <logical-name> --componentType 1` if needed, then re-verify. Do this for both tables.
2. **Systemuser lookup relationship naming**: the SDK's `create_lookup_field()` convenience wrapper auto-generates an invalid relationship schema name for lookups to built-in tables like `systemuser`. Use `create_one_to_many_relationship()` directly with an explicit `rpo_`-prefixed name (e.g. `rpo_SeasonResultEntry_Employee`) for the employee lookup on `rpo_SeasonResultEntry`.
3. **DateTime columns**: creating via generic `add_columns()`/`create()` with a plain `"datetime"` string leaves `DateTimeBehavior` unset and breaks later metadata operations irreversibly (short of delete+recreate). Create `computedat` via a raw Web API call with explicit `Format` (`DateAndTime`) and `DateTimeBehavior` (`UserLocal`) from the start.
