## Design note (simpler than layer 8's Season Result — do NOT copy that pattern)
Unlike `Season Result` (which stores a full ranked LIST and needed a child table), `Hall of Fame Entry` stores exactly ONE winner per season+category (the top-1, crowned at season close). This does NOT need a child table — model the polymorphic "winner (employee or poutine)" directly on `rpo_HallOfFameEntry` as two nullable lookups (to `systemuser` for employee-type categories, to `rpo_PoutineSubmission` for poutine-type categories), exactly one populated per row depending on the category's computation type — same polymorphic pattern as layer 8's `rpo_SeasonResultEntry`, just without the parent/child split.

## Reusable gotchas from prior layers
1. **Solution attachment**: SDK's `client.tables.create(..., solution=...)` doesn't reliably auto-attach new tables to `poutineleaguecore`'s solutioncomponent list. After creating the table, explicitly verify solution membership and fix with `pac solution add-solution-component --component <logical-name> --componentType 1` if needed, then re-verify.
2. **Systemuser lookup relationship naming**: SDK's `create_lookup_field()` wrapper generates an invalid relationship name for lookups to built-in tables like `systemuser`. Use `create_one_to_many_relationship()` directly with an explicit `rpo_`-prefixed name (e.g. `rpo_HallOfFameEntry_Employee`) for the employee lookup.
3. **DateTime columns**: not expected to apply here (Hall of Fame Entry has no date/time field per ARCHITECTURE.md), but if you add one, use a raw Web API call with explicit Format + DateTimeBehavior, never the SDK's generic "datetime" string type.
